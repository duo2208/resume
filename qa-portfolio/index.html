테스트의 구조화

반복 가능한 검증은 기준과 시스템으로 만들고, QA의 판단은 더 중요한 문제에 집중하도록 했습니다.
테스트 정책과 케이스를 자산화하고, 반복 회귀는 자동화했으며, AI를 활용해 테스트 설계 과정까지 구조화했습니다.

WMS는 상품 등록, 입고, 출고, 택배 연동, CS가 하나의 업무 흐름으로 이어집니다. 리뉴얼에서 확인해야 할 것은 화면이 잘 뜨는지가 아니라, 기존 업무 흐름과 데이터 정합성이 새 시스템에서도 유지되는지였습니다.

검증 범위 3개 권한 × 업무 전 구간
상품등록고객사필수값 · 중복
입고물류사수량 · 재고 반영
출고마스터주문 · 상태 전이
택배 연동마스터접수 · 송장
CS고객사취소 · 반품 정합성

3PL/1PL 물류사와 셀러 유형을 조합해 7개 업무 시나리오를 구성하고, 마스터·물류사·고객사 권한별 기능과 데이터 흐름을 교차 검증했습니다.

검증 단계 7 Business Scenarios · 533+ TC · 418 Defects
  1. 1차 단위테스트

    TC 기반으로 메뉴별 기능을 검증했습니다.

  2. 권한별 탐색 테스트

    사이드 이펙트를 고려해 권한별 전체 메뉴를 탐색 테스트로 검증했습니다. 사전에 정의한 TC 밖의 결함도 이 과정에서 다수 발견했습니다.

  3. 시나리오 테스트

    셀러 유형별 업무 흐름을 End-to-End로 이었습니다.

  4. 추가 개발 메뉴 테스트

    리뉴얼과 함께 신규 개발된 재고 관리 메뉴를 별도 범위로 검증했습니다.

  5. 운송장 출력 전수검사

    택배사별 출력 규격을 전수 검증했습니다.

  6. 자동화 검수 모니터링

    자동화 검수 결과의 에러 로그를 모니터링하고 이슈를 보고했습니다.

그러려니 넘기지 않고, 기준을 다시 확인했습니다

구현 방식이 달라졌다면 경계값도 다시 봅니다

PHP/Java 기반 시스템이 Vue.js로 전환되면서 숫자 입력값을 처리하는 방식에도 차이가 생긴다는 점을 인지했습니다. 경계값을 검증해 잘못된 값이 저장되는 오류를 발견하고, 입력 단계에서 유효성 검사를 적용하도록 제안했습니다.

연결된 상태를 확인합니다

개별 화면의 정상 동작만 보지 않고 주문·택배 등 연동된 정보까지 함께 검증했습니다. 그 과정에서 간헐적으로 접수가 실패해도 ‘접수 요청’ 상태에 그대로 머무는 것을 발견해, 별도 실패 상태값 도입을 제안하고 고객 이관 테스트 체크리스트에 반영했습니다.

이전 경험도 새로운 도메인의 검증 기준으로 씁니다

검색 솔루션 개발 경험을 바탕으로 검색 정확도를 검증하면서, 공통 검색 정책을 일부 필드에는 그대로 적용할 수 없는 예외를 발견했습니다. 공통 정책과 예외 조건을 구분해 시스템 가이드라인에 반영했습니다.
