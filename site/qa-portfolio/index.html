어떤 QA인가

사업 일정과 출시 목적을 고려해 QA를 수행합니다
콘텐츠 커머스 · 시즌 프로모션 · 출시 대응

콘텐츠 IP 상품의 구매 동기와 시즌별 판매 시점을 이해하고, MD 일정에 따라 단기간에 기능 반영이 필요한 프로젝트의 QA를 주로 담당했습니다. 덕키박스에서는 추석 시즌 판매와 온라인 구매 기회 확대라는 출시 목적을 바탕으로, 변경되는 요구사항과 일정에 대응하며 검수를 수행했습니다.

실제 동작을 근거로 원인을 좁힙니다
화면 · API · 데이터 · 기기 환경

화면의 결과를 API 응답·DB 이력·기기 로그와 대조해 문제가 발생하는 조건과 지점을 좁힙니다. 확인한 근거를 개발팀과 공유하고, 수정 후 같은 조건에서 다시 검증합니다.

협업 부서의 자율 검증을 지원합니다
검수 정보 체계화 · 테스트 접근성 · 협업 효율

분산된 테스트 환경과 관리자 접근 정보를 정리해, 협업 부서가 검수에 필요한 정보를 직접 확인할 수 있도록 했습니다. 비개발 직군도 별도 문의 없이 자가 검수를 진행할 수 있도록 지원하며, QA에 집중되던 정보 확인과 안내 부담을 줄이고자 했습니다.

반복되는 제약은 방법을 바꿔 해결합니다
테스트 자동화 · AI 활용 · 테스트 데이터 준비

반복 검수를 자동화하고, 요구사항을 바탕으로 테스트 케이스 초안을 생성하는 AI 도구를 개발했습니다. 검수 조건에 맞는 테스트 계정도 사전에 구성해, 테스트 준비부터 실행까지 반복되는 수작업을 줄이는 방향으로 업무 방식을 개선했습니다.

테스트 환경 개선

테스트 케이스 작성과 데이터 준비를 돕는 도구를 만들고, 결제 검수 절차를 문서로 정리했습니다.
반복 회귀는 E2E 자동화로 확인하고, 동시 접속 상황은 부하 테스트로 재현해 입장·재생 요청의 실패 양상을 살폈습니다.

여러 스쿼드의 전수 검증을 병행하면서, 환경을 초기화할 때마다 테스트 데이터를 다시 준비해야 했습니다. 회고에서 데이터 준비에 드는 시간을 줄이기 위해, “온홀드 상태로 만들어줘”처럼 계정·결제·콘텐츠 상태를 한 번에 만들 수 있는 어드민 MCP 도입을 제안했습니다.

백엔드와 협업해 테스트 계정과 데이터를 사전에 준비하여, 디자인팀과의 반복적인 확인·조율과 전체 검수 시간을 줄였습니다. 사전 데이터로 검증할 수 있는 범위를 구분해 검수 프로세스에 반영했으며, 확인된 효용을 바탕으로 고도화를 이어가기로 했습니다.

04

선행 상영회 입장·재생 부하 검증

동시 접속 시 어느 단계부터 실패하는가

선행 상영회에 접속이 몰릴 때 입장과 방송 시작 시 재생 요청이 정상적으로 처리되는지를 확인하기 위해 상용과 가장 유사한 서버 구성을 갖춘 환경에서 JMeter로 동시 입장·대기·방송 시작·추가 입장 상황을 검증했습니다. 대량 계정 준비는 AI의 도움으로 스크립트화했습니다. 테스트 계정의 로그인을 미리 마친 뒤, 로그인된 사용자들이 동시에 상영회에 입장하도록 구성했습니다.

테스트 결과 대기 중 채팅보다 입장과 방송 시작 순간의 재생 요청이 먼저 실패하는 양상을 확인했습니다. 시청자가 쌓이면서 홈·상영회 조회도 느려졌고, 함께 테스트한 개발자는 방송 시작 후 추가 입장 과정에서 서버가 응답하지 않는 상황을 공유했습니다. 단계별 실패 양상과 서비스 이용에 미치는 리스크를 팀에 공유했습니다.

서버 정기 배포와 QA 스쿼드 배포 관련 검증에도 활용했습니다. 2026년 7월에는 배포 후 시간이 지나 발생한 라이브·이벤트 페이지 장애가 운영 E2E 테스트에서도 확인됐습니다. 후속 조사에서 운영 환경 설정 문제가 확인됐으며, 재배포 전에는 QA 환경에서 부하 테스트를 수행해 이상 응답 여부를 점검했습니다.
