테스트의 구조화

반복 가능한 검증은 기준과 시스템으로 만들고, QA의 판단은 더 중요한 문제에 집중하도록 했습니다.
테스트 정책과 케이스를 자산화하고, 반복 회귀는 자동화했으며, AI를 활용해 테스트 설계 과정까지 구조화했습니다.

02. Apple In-App 결제

Native In-App · 구독 상태 머신 · 상태 전이 검증
Payment QA

App Store 결제는 구독 상태가 올바르게 전이되는지가 중요했습니다.
Pending, OnHold, 복원 등 상태가 하나의 흐름으로 이어지기 때문에 상태 전이를 기준으로 검증했습니다.

PROBLEM

결제 결과뿐 아니라 StoreKit 상태에 따라
권한 · UI · API 가 서로 다르게 동작했습니다.

ACTION

구독 상태를 상태 머신으로 정리하고 Pending, On Hold, 복원 등 주요 상태 전이를 기준으로 검증 시나리오를 설계했습니다.

RESULT

상태 전이 기준으로 결제 검증을 표준화해 결제 관련 CS를 사실상 0건으로 줄였고, 애플 Billing Retry 상태의 회원 탈퇴 원인을 특정했습니다.

샌드박스에서는 깨끗한 계정으로 테스트하는 것이 권장되지만, 실제 서비스에서는 기존 Google/PG 결제 이력이 남은 상태에서 Apple 결제가 시작될 수 있습니다. 실제 사용자 환경을 고려해 결제 이력이 혼합된 계정까지 검증하며, 결제 수단 전환 시 서버 상태가 올바르게 동기화되는지 확인했습니다.

01. 계정 체계 개선

Dummy Account · Social Login · 필수 정보 조합 검증 / CS 감소
Account QA
PROBLEM

가입 중 이탈로 정보가 누락된 더미 계정이 반복 CS를 만들었습니다.

ACTION

계정이 어떤 상태로 남을 수 있는지 먼저 구조화한 뒤, 각 상태에서 로그인·결제·탈퇴까지 이어지는 흐름을 하나씩 검증했습니다.

RESULT

배포 후 이메일 미인증 계정을 30~37% 줄였고, 더미 계정으로 인한 고객 문의도 크게 감소했습니다.

Experiment QA
PROBLEM

실험 결과보다 먼저, 실험 환경이 신뢰할 수 있는지 검증해야 했습니다.

ACTION

RESULT

QA가 원하는 실험군을 안정적으로 재현할 수 있는 환경을 마련했고, 실험군 분배와 데이터 오염 리스크를 검증했습니다.

04. B2B 제휴 검증

Partnership · External API · Reverse Spec · 현장 검수
Partnership QA

PC방 제휴는 라프텔과 외부 사업자가 하나의 서비스를 함께 운영하는 프로젝트였습니다. 멤버십 권한, 동시 재생, 이용 시간 정산처럼 서비스 경계가 두 시스템에 나뉘어 있었고, 문서에 없는 동작은 실제 응답과 화면을 비교하며 검증 기준을 직접 정리해야 했습니다.

PROBLEM

문서만으로는 정상 동작을 판단하기 어려운 응답과 정책 차이가 존재했습니다.

ACTION

에러 응답을 역분석해 Reverse Spec을 만들고, 동시 재생·과금·권한 경계를 분리했습니다.

RESULT

제휴 환경에서도 일관된 기준으로 품질을 검증할 수 있는 프로토콜을 만들었습니다.

06. 배포 장애 후 재배포 안전성 검증

JMeter · 재배포 안전성 부하 검증 · 신규 스택 성능 리스크 점검
Performance QA

프레임워크 메이저 업그레이드 배포 후 일부 페이지에서 500 장애가 발생해 롤백됐고, 원인은 배포 환경 설정 이슈로 요청이 정상 처리되지 않는 현상으로 이미 확인된 상태였습니다. 저는 “설정만 고쳐 재배포하면 정말 안전한가”를 QA 환경에서 부하로 확인해야 했고, JMeter로 주요 페이지와 핵심 API에 부하를 걸어 응답시간·throughput을 분석하며 잠재적인 성능 병목과 재배포 위험을 점검했습니다.

PROBLEM

장애 원인은 배포 환경 설정 이슈로 확인됐지만, 설정만 수정하면 재배포해도 안전한지는 근거가 없었습니다.

ACTION

JMeter로 요청률을 제어해 주요 페이지와 핵심 API에 단계별 부하를 걸고, throughput · p95 응답시간 · 에러율을 측정하며 재배포 시 재발 가능성을 분석했습니다.

RESULT

설정 수정 외에 신규 스택의 성능 병목 여부까지 함께 점검했고, QA 환경 관측치와 그 한계를 함께 리포트해 재배포 리스크를 데이터 기반으로 판단할 근거를 마련했습니다.
